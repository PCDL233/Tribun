# AI Code Review Agent — 代码编写规范（TypeScript Monorepo）

> **适用范围**：本规范适用于本项目 Monorepo 中的全部代码，包括 `apps/*`（cli、server、web）、`packages/*`（shared、diff、core、agents、tools、rag、llm、db、report）与 `tooling/*`。
>
> **参考基准**：本规范以 [Google TypeScript Style Guide](https://google.github.io/styleguide/tsguide.html) 为主基准，并结合 [Airbnb JavaScript/React Style Guide](https://github.com/airbnb/javascript)、[Microsoft TypeScript 编码约定](https://github.com/microsoft/TypeScript/wiki/Coding-guidelines) 与 Vercel AI SDK 官方示例约定制定。凡本规范未覆盖之处，以上述外部规范为准。

---

## 0. 规范等级

本文使用 RFC 2119 风格的关键词，含义如下：

| 关键词 | 含义 | 违反后果 |
|--------|------|---------|
| **必须（MUST）** | 强制约束 | Code Review 直接打回，CI lint 必须拦截 |
| **应当（SHOULD）** | 强烈建议 | 偏离时必须在代码注释或 PR 描述中给出理由 |
| **可以（MAY）** | 允许的选择 | 团队内保持一致即可 |

---

## 1. 总则

1. **必须** 遵循"确定性优先"原则：能用类型系统、编译期检查和确定性工具保证的事情，不留给运行时，更不留给 LLM 判断。
2. **必须** 通过 `pnpm turbo lint && pnpm turbo typecheck && pnpm turbo test`，任何一步失败不得合入。
3. **必须** 以 `packages/shared` 的 zod schema 为单一事实源，**禁止** 在任何包中手工重复定义 shared 中已有的类型。
4. **应当** 让代码"读起来像设计方案"：函数名、类名、状态字段名与《项目实现方案》中的模块设计一一对应（如 `RiskPlanner`、`DiffContextBuilder`、`healRounds`），不做无来源的二次命名。
5. **禁止** 提交与当前任务无关的"顺手重构"，重构必须单独成 PR/commit。

## 2. 命名规范

### 2.1 通用规则

| 对象 | 规则 | 示例 |
|------|------|------|
| 变量、函数、方法 | `camelCase` | `contextRadius`、`buildFileContext` |
| 类、接口、类型别名、枚举 | `PascalCase` | `DiffContextBuilder`、`ReviewPlan` |
| 枚举成员 | `PascalCase` | `Severity.Blocker` |
| 模块级常量 | `UPPER_SNAKE_CASE` | `HIGH_RISK_PATTERNS`、`DECISION_KINDS` |
| 类型参数 | 单个大写字母或 `T` + 描述性词 | `T`、`TContext` |
| 文件名（非组件） | `kebab-case` | `risk-planner.ts`、`context-builder.ts` |
| React 组件文件名 | `PascalCase` | `ReviewReportCard.tsx` |
| 目录名 | `kebab-case` | `cross-validate/` |
| 包名 | `@ai-review/<kebab-case>` | `@ai-review/shared` |

### 2.2 接口与类型

- **必须** 遵循 Google 规范：接口名**不加** `I` 前缀。写 `FileHistory`，不写 `IFileHistory`。
- **应当** 优先使用 `type` 而非 `interface`（Google 规则），联合类型、工具类型、zod 推导类型只能用 `type`：

  ```typescript
  // ✅ 正确
  export type ScoredFile = { diff: FileDiff; score: number };
  export type ReviewPlan = { deep: ScoredFile[]; quick: ScoredFile[]; staticOnly: ScoredFile[] };

  // ❌ 错误：为对象类型引入 interface 仅为风格偏好，且禁止 I 前缀
  export interface IScoredFile { ... }
  ```

- **必须** 从 zod schema 推导类型，**禁止** 手写与之重复的形状：

  ```typescript
  // ✅ 正确（packages/shared/src/config.ts）
  export const AiReviewConfigSchema = z.object({ /* ... */ });
  export type AiReviewConfig = z.infer<typeof AiReviewConfigSchema>;

  // ❌ 错误：手写 AiReviewConfig 接口，与 schema 双源
  ```

### 2.3 zod Schema 命名

- Schema 变量 **必须** 以 `Schema` 结尾：`AiReviewConfigSchema`、`FindingSchema`。
- 多个字段共享的子 schema 提取为命名常量，不内联复制。

### 2.4 布尔命名

- **必须** 以 `is` / `has` / `should` / `can` 开头：`isAsync`、`hasStagedChanges`、`shouldBlockCommit`。
- **禁止** 否则式命名（`isNotEmpty` 一类双重否定），存疑时改为肯定语义。

### 2.5 异步与领域命名

- 返回 `Promise` 的函数名不强制 `async` 前缀，但领域动作要具体：`build()`、`plan()`、`review()`、`query()`、`account()`。
- 事件/回调以 `on` 开头：`onExhausted`、`onProgress`。
- 工厂/装配函数以 `build` / `make` / `create` 开头：`buildModelChain()`、`buildPipeline()`、`makeReviewNode()`（对齐方案文档用法）。
- LangGraph 状态字段与方案文档保持一致：`context`、`plan`、`findings`、`healRounds`、`metrics`，**禁止** 同义替换。

### 2.6 禁止项

- **禁止** 拼音、无意义缩写（`data2`、`tmp`、`foo`）、匈牙利命名。
- **禁止** 单字母命名，循环变量 `i/j/k` 与类型参数除外。
- **禁止** 命名中携带类型信息（`strName`、`userArray`）。

## 3. 函数与方法规范

### 3.1 尺寸与职责

- **应当** 单个函数不超过 **50 行**、圈复杂度不超过 **15**（与方案中静态分析阈值一致——我们审查别人代码的标准，首先适用于自己的代码）。超标时拆分为具名私有函数。
- **必须** 单一职责：一个函数只做一层抽象的事。如 `DiffContextBuilder.build()` 只做"取 diff → 过滤 → 并行构建 → 汇总"的编排，文件级细节下沉到 `buildFileContext()`。

### 3.2 签名

- **必须** 为导出函数与公有方法显式标注返回类型（Google 规则），推导类型仅允许用于局部变量：

  ```typescript
  // ✅ 正确
  export function analyzeComplexity(source: string, threshold = 15): FunctionMetrics[] { ... }
  export function loadConfig(path = ".ai-review.yml"): AiReviewConfig { ... }

  // ❌ 错误：导出函数省略返回类型
  export function loadConfig(path = ".ai-review.yml") { ... }
  ```

- **必须** 参数不超过 4 个，超过时改为对象参数并导出其类型：

  ```typescript
  // ❌ 错误
  function runReview(repoPath: string, mode: Mode, blockOn: Severity, json: boolean, output?: string) { ... }

  // ✅ 正确
  type RunReviewOptions = { repoPath: string; mode: Mode; blockOn: Severity; json: boolean; output?: string };
  function runReview(opts: RunReviewOptions): Promise<ExitCode> { ... }
  ```

- **应当** 依赖注入用构造器参数，可运行时配置用带默认值的尾参数（如 `contextRadius: number = 50`、`threshold = 15`）。

### 3.3 控制流

- **应当** 使用早返回（guard clause）减少嵌套，嵌套深度不超过 **4 层**（与方案中"过深嵌套 > 4 层"检测项一致）：

  ```typescript
  // ✅ 正确
  for (const diff of diffs) {
    if (isTestOrDocs(path) || isFormattingOnly(diff)) {
      score = Math.max(0, score - 25);
      continue; // 降权后不再叠加其他维度
    }
    // ...
  }

  // ❌ 错误：if/else 层层包裹
  ```

- **禁止** 函数内混用 `return` 裸值与 `return await`；异步函数中 `Promise` 必须显式 `await` 或显式返回，不允许悬空调用。

### 3.4 纯函数优先

- **可以** 建类承载"多方法共享构造期依赖"的逻辑（`DiffContextBuilder`、`KnowledgeBase`）；无状态逻辑**应当**写成导出的纯函数（`rrfFuse`、`parseFindings`、`routeAfterValidate`）。
- **禁止** 通过模块级可变变量在函数间隐式传状态；跨节点的共享状态只能放入 LangGraph 的 `ReviewState`。

## 4. 类与对象规范

### 4.1 构造器与依赖注入

- **必须** 用构造器注入依赖，注入字段一律声明为 `private readonly` / `protected readonly`（Microsoft 规范，对齐方案代码）：

  ```typescript
  // ✅ 正确（packages/diff/src/context-builder.ts）
  export class DiffContextBuilder {
    constructor(
      private readonly repoPath: string,
      private readonly rag: RagRetriever,
      private readonly ignores: IgnoreRules,
      private readonly contextRadius: number = 50,
    ) {}
  }

  // ❌ 错误：public 可变依赖、构造后再赋值
  export class DiffContextBuilder {
    rag: RagRetriever;            // 未 readonly
    constructor(rag: RagRetriever) { this.rag = rag; }
  }
  ```

- **必须** 依赖面向接口类型（`RagRetriever`、`GitRunner`、`FileHistory`），而非具体实现，保证测试可用 fixture 替换。

### 4.2 成员组织与可见性

- 成员声明顺序 **必须** 为：`static` 字段 → `static` 方法 → 实例字段 → 构造器 → getter/setter → 公有方法 → 私有方法（对齐 `TokenBudget` 的写法：私有字段 → 构造器 → 方法 → getter）。
- **应当** 最小可见性：能 `private` 不 `public`，能不导出类就不导出（`makeReviewNode` 这类工厂内部逻辑不外泄）。
- **禁止** 暴露可变集合：返回数组/对象时给出防御性副本或 `Readonly` 类型。

### 4.3 组合优先

- **必须** 组合优于继承；确需继承时只允许单层 `extends` 且基类标记为 `abstract`。
- **禁止** 为"未来可能的复用"提前抽象（YAGNI）；抽象只发生在出现第二个真实使用方时。

### 4.4 不可变性

- **必须** 类实例字段除明确需要变更者外一律 `readonly`（如 `TokenBudget.max`、`ReviewAgent.model`）。
- `TokenBudget.used` 这类**有意**可变的内部状态，**必须** 私有且只通过方法修改（`tryReserve`、`account`）。

## 5. 类型与 Schema 规范

1. **必须** 全仓 `strict: true`（`tooling/tsconfig` 基线），并开启 `noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`。
2. **禁止** `any`；不确定类型用 `unknown` + 类型收窄。
3. **禁止** `as` 类型断言与 `!` 非空断言，以下两种情况除外（且必须注释原因）：
   - zod `parse()` 之后的产出；
   - LangGraph 生命周期保证非空的外部资源（如 `KnowledgeBase.query()` 中的 `this.table!`——`build()` 已先行调用），断言处**必须**留注释说明保证来源。
4. **禁止** `@ts-ignore`；确需豁免用 `@ts-expect-error` 并附注释，使类型修好后编译报错提醒清理。
5. **必须** 用 zod 校验一切跨越边界的运行时数据，四条链路不得绕过（见方案 2.3）：
   - 配置文件（`loadConfig` → `AiReviewConfigSchema.parse`）；
   - API 入参（Hono `zValidator`）；
   - LLM 输出（`parseFindings` 解析失败即触发自愈回退，**禁止**静默吞掉）；
   - 数据库行类型（Drizzle schema 与 shared 类型对齐）。
6. **必须** 类型导入使用 `import type`，与值导入分离（见方案代码惯例）：

   ```typescript
   import { z } from "zod";
   import type { FileDiff, ReviewPlan } from "@ai-review/shared";
   ```

7. **必须** 字面量联合优先于 `enum`（Google 规则）；确需运行时枚举对象时用 `as const` + `Object.freeze` 风格。严重度等领域词汇统一为 `BLOCKER / WARNING / NIT / PRAISE` 字符串字面量，与退出码契约、报告格式保持一致，**禁止**另造同义词。

## 6. 方法调用与 API 使用约定

1. **必须** Node 内置模块以 `node:` 前缀导入：`import { execFile } from "node:child_process"`。
2. **必须** 子进程调用显式传参数组（`exec("git", args, { cwd })`），**禁止** 字符串拼接 shell 命令（规避 Windows 转义差异，对齐方案 5.1 的兼容性约定）。
3. **必须** 统一并发控制原语：批量 I/O 用 `p-map`（指定 `concurrency`），单资源限流用 `p-limit`，**禁止** 手写无上限的 `Promise.all` 扇出：

   ```typescript
   const contexts = await pMap(meaningful, (d) => this.buildFileContext(d, git), { concurrency: 8 });
   const fileGate = pLimit(8); // 单 Agent 内文件级并发限流
   ```

4. **必须** 空值访问使用可选链 `?.` 与空值合并 `??`；`??` 与 `||` 的语义差异必须明确（`0`、`""`、`false` 是合法值时只能用 `??`）。
5. **必须** 工具调用统一经 Tool Bus 注册（进程内）或 MCP（对外），**禁止** 各 Agent 直接 import 具体工具实现绕过总线。
6. **应当** LLM 调用统一走 `packages/llm` 封装（Provider 链、预算、重试），业务包 **禁止** 直接 `import { createAnthropic }`。
7. **禁止** 在代码中硬编码密钥、模型端点等环境相关值；配置一律来自 `.ai-review.yml`（经 schema 校验）+ `${ENV}` 引用。

## 7. 异步与错误处理规范

1. **必须** 所有新代码使用 `async/await`，**禁止** 混用回调式 API（Node 内置回调 API 先 `promisify`，对齐方案 `context-builder.ts` 写法）。
2. **必须** 支持取消：所有可能长时间运行的异步入口透传 `AbortSignal`（LLM 调用、流水线 `app.invoke(..., { signal })`），**禁止** 遗弃 signal 参数。
3. **必须** token 消耗计入共享 `TokenBudget`；预算耗尽走降级路径并在报告中标注，**禁止** 绕过预算器直接调用模型。
4. **错误处理三选一**，**禁止** 静默吞错：

   ```typescript
   // ✅ 允许：有明确降级语义的 catch（删除文件时 index 中无 blob → 降级为仅 diff 审查）
   const stagedContent = await git("show", `:${diff.path}`).catch(() => "");

   // ✅ 允许：捕获后转译并重新抛出
   try { ... } catch (e) { throw new ConfigError(`failed to load ${path}`, { cause: e }); }

   // ❌ 禁止：空 catch / 仅 console.log / Promise 上挂 .catch(() => {}) 而无语义
   ```

5. **必须** 自定义错误类继承 `Error` 并命名以 `Error` 结尾（`ConfigError`、`PipelineTimeoutError`），携带 `cause`；**禁止** `throw` 字符串或普通对象。
6. **必须** 遵守 CLI 退出码契约（0 通过 / 1 阻断 / 2 配置环境错误 / 3 超时取消），**禁止** 新增退出码或改变语义；任何退出码变更属于破坏性契约变更。
7. **应当** 面向流水线的代码把错误分类为"可降级"（记录后继续，如 Tree-sitter 解析失败退化为行级分析）与"应中止"（配置错误、仓库无效），在 catch 点明确走向。

## 8. 注释与文档规范

1. **必须** 为所有导出符号编写 TSDoc（`/** ... */`），包含用途、参数与异常；私有实现不需要逐行注释。
2. **必须** 注释解释"为什么"，而不是复述代码"做了什么"：

   ```typescript
   // ✅ 正确（节选自方案 context-builder.ts）
   /**
    * 核心正确性约定：审查对象是暂存区（index）快照，而不是工作区。
    * pre-commit 阶段工作区可能包含未暂存改动，只有 index 内容才与本次 commit 一致。
    */
   async build(): Promise<CodeContext> { ... }
   ```

3. **必须** 在以下位置强制注释：
   - 正确性敏感约定（如"以 index 为唯一事实源"、RRF 融合顺序）；
   - 魔法数值来源（风险评分 `≥60 / 40~60 / <40` 分流阈值、复杂度阈值 15）；
   - 与外部契约的耦合点（退出码、MCP 工具名、SSE 事件结构、`block_on` 阈值）。
4. **应当** 使用 JSDoc 标签：`@param`、`@returns`、`@throws`、`@deprecated`（弃用符号必须说明替代方案与移除计划）。
5. **禁止** 提交被注释掉的死代码、`TODO` 无负责人或无编号的注释。`TODO(name): #issue` 为合法格式。
6. **可以** 用中文撰写注释与 TSDoc；标识符、报错信息与日志一律英文。

## 9. 前端专项（React 19 + Vite 8）

1. **组件**：函数组件，`PascalCase` 命名，一个文件一个组件；props 类型命名 `XxxProps` 并导出。
2. **禁止** 手写 `useMemo` / `useCallback` / `React.memo`——项目启用 React Compiler 自动 memoization（方案 3.10）；确需手写时必须在 PR 中说明 Compiler 无法覆盖的原因。
3. **状态分层**：
   - 服务端状态（审查历史、报告详情、统计）**必须** 用 TanStack Query，**禁止** 用 `useEffect` + `useState` 手工拉取；
   - 实时进度 **必须** 走 SSE 自定义 hook 订阅；
   - 乐观更新（如误报标记）**必须** 用 `useOptimistic` 并处理回写失败回滚。
4. **类型共享**：API 响应类型 **必须** `import type` 自 `@ai-review/shared`，**禁止** 在 `apps/web` 内手写 API 形状。
5. **Hooks 顺序**：遵守 Rules of Hooks（ESLint `react-hooks/rules-of-hooks` 强制）；自定义 hook 以 `use` 开头。
6. **组件拆分**：单组件（含 JSX）超过约 200 行应当拆分；列表项、卡片等重复结构提取为独立组件。
7. **样式与文案**：使用 Ant Design 6 组件体系，不混用原生样式；用户可见文案中文，代码标识英文。

## 10. 格式化与工具链落地

1. **必须** 由 Prettier 统一格式（2 空格缩进、单引号、行宽 100、尾逗号 `all`），提交前经 `lint-staged` 自动格式化，**禁止** 人工调整格式或在 Review 中讨论格式。
2. **import 顺序**（由 ESLint `simple-import-sort` 或 `import-x/order` 强制）：
   1. `node:` 内置模块；
   2. 第三方库（`zod`、`ai`、`@langchain/langgraph` 等）；
   3. Monorepo 内部包（`@ai-review/*`）；
   4. 本包相对路径（`./parser`）；
   5. 纯类型导入（`import type`）紧随各分组或独立成组，保持全仓一致。
3. **关键 ESLint/oxlint 规则基线**（`tooling/eslint-config` 统一下发）：

   | 规范条目 | 强制规则 |
   |----------|---------|
   | 禁 `any` / 断言 | `@typescript-eslint/no-explicit-any`、`no-unsafe-*` 系列 |
   | 禁 `@ts-ignore` | `@typescript-eslint/ban-ts-comment` |
   | 未决 Promise | `@typescript-eslint/no-floating-promises`、`no-misused-promises` |
   | 返回类型注解 | `@typescript-eslint/explicit-function-return-type`（限导出） |
   | 空 catch | `no-empty` |
   | 命名 | `@typescript-eslint/naming-convention` |
   | Hooks | `react-hooks/rules-of-hooks`、`react-hooks/exhaustive-deps` |
   | import 排序 | `simple-import-sort/imports` |

4. **必须** 依赖版本只声明在 `pnpm-workspace.yaml` 的 `catalog`，各包以 `catalog:` 协议引用；**禁止** 在包级 `package.json` 中直接写版本号。
5. **必须** 新增包/任务时同步更新 `turbo.json` 任务图与 `tsconfig` 引用，保证 `typecheck`/`test` 的依赖顺序正确。

## 11. Git 提交规范（Conventional Commits）

1. **必须** 提交信息格式：`<type>(<scope>): <subject>`，例如：

   ```text
   feat(agents): 正确性审查 Agent 支持 LOW_CONFIDENCE 标记
   fix(diff): 修复 CRLF 文件在 Windows 下的行号偏移
   refactor(core): 抽取 routeAfterValidate 条件边为独立纯函数
   docs(shared): 补充 AiReviewConfigSchema 字段说明
   ```

2. **type 取值**：`feat` / `fix` / `docs` / `refactor` / `perf` / `test` / `build` / `ci` / `chore` / `revert`；scope 取包名短名（`cli`、`server`、`web`、`core`、`agents`、`tools`、`rag`、`llm`、`db`、`report`、`diff`、`shared`）。
3. **必须** subject 使用祈使句、结尾不加句号；正文说明"为什么"（动机与取舍），改动本身由 diff 呈现。
4. **必须** 破坏性变更在 type 后加 `!` 并在正文标注 `BREAKING CHANGE:`（如修改退出码契约、MCP 工具入参）。
5. **应当** 一次提交一个完整逻辑单元；`lint-staged` + husky `pre-commit` 钩子自动执行 lint 与 fast 模式审查。
